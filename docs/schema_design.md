# Schema Design

## Overview

This document defines the initial relational database schema for storing NASA NeoWs data in SQLite.

The schema is designed to:

* Normalize nested JSON structures
* Eliminate duplicate asteroid records
* Support asteroid-to-approach relationships
* Store orbital characteristics separately from core asteroid records
* Enable efficient querying and future analytics

---

# Table: asteroids

## Purpose

Stores one row per unique Near-Earth Object (NEO) returned by the NASA NeoWs API.

## Schema

| Column                    | Type    | Constraints | Source                                                 |
| ------------------------- | ------- | ----------- | ------------------------------------------------------ |
| asteroid_id               | TEXT    | PRIMARY KEY | `id`                                                   |
| self_link                 | TEXT    | NOT NULL    | `links.self`                                           |
| name                      | TEXT    | NOT NULL    | `name`                                                 |
| absolute_magnitude_h      | REAL    | NULL        | `absolute_magnitude_h`                                 |
| estimated_diameter_min_km | REAL    | NULL        | `estimated_diameter.kilometers.estimated_diameter_min` |
| estimated_diameter_max_km | REAL    | NULL        | `estimated_diameter.kilometers.estimated_diameter_max` |
| is_potentially_hazardous  | INTEGER | NOT NULL    | `is_potentially_hazardous_asteroid`                    |

## Draft SQL

```sql
CREATE TABLE asteroids (
    asteroid_id TEXT PRIMARY KEY,
    self_link TEXT NOT NULL,
    name TEXT NOT NULL,
    absolute_magnitude_h REAL,
    estimated_diameter_min_km REAL,
    estimated_diameter_max_km REAL,
    is_potentially_hazardous INTEGER NOT NULL
        CHECK (is_potentially_hazardous IN (0, 1))
);
```

## Notes

* Uses NASA's asteroid ID as the primary key.
* Stores one row per unique asteroid.
* Diameter values are flattened from the nested JSON structure.
* Boolean values are stored as SQLite integers (`0` = false, `1` = true).

# Table: close_approaches

## Purpose

Stores one row per asteroid close-approach event.

A single asteroid may have multiple close-approach records.

## Schema

| Column                | Type    | Constraints               | Source                                                      |
| --------------------- | ------- | ------------------------- | ----------------------------------------------------------- |
| approach_id           | INTEGER | PRIMARY KEY AUTOINCREMENT | Generated                                                   |
| asteroid_id           | TEXT    | NOT NULL, FOREIGN KEY     | `asteroids.asteroid_id`                                     |
| close_approach_date   | TEXT    | NOT NULL                  | `close_approach_data.close_approach_date`                   |
| relative_velocity_kph | REAL    | NULL                      | `close_approach_data.relative_velocity.kilometers_per_hour` |
| miss_distance_km      | REAL    | NULL                      | `close_approach_data.miss_distance.kilometers`              |
| orbiting_body         | TEXT    | NOT NULL                  | `close_approach_data.orbiting_body`                         |

## Draft SQL

```sql
CREATE TABLE close_approaches (
    approach_id INTEGER PRIMARY KEY AUTOINCREMENT,
    asteroid_id TEXT NOT NULL,
    close_approach_date TEXT NOT NULL,
    relative_velocity_kph REAL,
    miss_distance_km REAL,
    orbiting_body TEXT NOT NULL,

    FOREIGN KEY (asteroid_id)
        REFERENCES asteroids (asteroid_id)
);
```

## Notes

* One asteroid can have many close-approach records.
* `approach_id` is generated by SQLite.
* `asteroid_id` maintains referential integrity between tables.
* Dates are stored as ISO 8601 formatted text (`YYYY-MM-DD`).
* Velocity and distance values are stored as floating-point numbers.

# Table: orbital_parameters

## Purpose

Stores orbital characteristics associated with an asteroid.

This table separates relatively static orbital information from frequently changing approach-event data.

## Schema

| Column         | Type | Constraints              | Source                                      |
| -------------- | ---- | ------------------------ | ------------------------------------------- |
| asteroid_id    | TEXT | PRIMARY KEY, FOREIGN KEY | `asteroids.asteroid_id`                     |
| orbit_class    | TEXT | NULL                     | `orbital_data.orbit_class.orbit_class_type` |
| eccentricity   | REAL | NULL                     | `orbital_data.eccentricity`                 |
| inclination    | REAL | NULL                     | `orbital_data.inclination`                  |
| orbital_period | REAL | NULL                     | `orbital_data.orbital_period`               |

## Draft SQL

```sql
CREATE TABLE orbital_parameters (
    asteroid_id TEXT PRIMARY KEY,
    orbit_class TEXT,
    eccentricity REAL,
    inclination REAL,
    orbital_period REAL,

    FOREIGN KEY (asteroid_id)
        REFERENCES asteroids (asteroid_id)
);
```

## Notes

* `asteroid_id` serves as both the primary key and foreign key.
* Creates a one-to-one relationship with `asteroids`.
* An asteroid may not have orbital data available depending on the API endpoint used.
* Orbital values are nullable to accommodate missing source data.

# Table: ingestion_log

## Purpose

Stores metadata about each ETL ingestion attempt.

This table provides operational visibility into the data pipeline and supports auditing, troubleshooting, performance monitoring, and reproducible ingestion.

## Schema

| Column              | Type    | Constraints               | Source                         |
| ------------------- | ------- | ------------------------- | ------------------------------ |
| ingestion_id        | INTEGER | PRIMARY KEY AUTOINCREMENT | Generated                      |
| source_file         | TEXT    | NOT NULL                  | Raw JSON file path             |
| ingestion_timestamp | TEXT    | NOT NULL                  | Generated during ETL execution |
| rows_processed      | INTEGER | NOT NULL                  | ETL process                    |
| status              | TEXT    | NOT NULL                  | ETL process                    |
| duration_seconds    | REAL    | NULL                      | ETL process                    |

## Draft SQL

```sql
CREATE TABLE ingestion_log (
    ingestion_id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_file TEXT NOT NULL,
    ingestion_timestamp TEXT NOT NULL,
    rows_processed INTEGER NOT NULL,
    status TEXT NOT NULL
        CHECK (status IN ('success', 'failed')),
    duration_seconds REAL
);
```

## Notes

* `ingestion_id` uniquely identifies an ingestion run.
* `source_file` stores the raw JSON file that was processed.
* `ingestion_timestamp` should be stored as an ISO 8601 timestamp.
* `rows_processed` tracks the number of records successfully handled by the ETL process.
* `status` indicates whether the ingestion succeeded or failed.
* `duration_seconds` records total execution time for performance monitoring.
* This table does not contain NASA asteroid data. It contains operational metadata about the ETL pipeline itself.
